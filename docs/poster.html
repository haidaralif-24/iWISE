Pip

A lightweight AI assistant window with safe local tool access
Haidar Ali Fawwaz Nasirodin
Faiq Abiyyu Asyam
Avandreda Giano Bestafa
Indonesia
iTECH — Software / Programming

Research Question

Can a free-tier cloud AI chat service be given controlled, auditable access to a student's local files using only local components — and how much of the resulting risk surface can a user-controlled permission layer close?

Aim

To build a desktop window that reuses the AI account a student already has, and gives that AI access to their own files under a boundary the student controls.

The artefact is then evaluated on three axes: does it function, what does it cost, and what does it stop. A working demo alone answers none of them.

Hypothesis / Engineering Goal

H1 · Capability
A free account can call a local tool server, with no API key and no local model.		Supported
H2 · Boundary
A user-controlled permission layer closes most of the risk surface.		Partly
H3 · Efficiency
Converting a document to Markdown reduces token cost.		Rejected
H3 revised
Reading fewer pages reduces token cost. Conversion was the control that isolated it.		Supported

H3 was written first and is reported as rejected. The rejection is the most useful result here: it stops the next student building a converter expecting a saving.

Background Research

  • Model Context Protocol — an open standard for exposing tools to an AI client over a transport it already speaks. It is what lets a cloud chat service call a process on the user's own machine.
  • MarkItDown — converts PDF, DOCX, PPTX and XLSX to Markdown. Chosen because conversion is solved and the interesting problem is the permission boundary.
  • Tauri — a Rust shell rendering the system webview. Chosen over Electron so that spawning a process is an explicit, reviewable command.

Existing AI desktop clients give an assistant file access, but the boundary is set by the vendor and the account is normally paid. The gap is the student on a free tier who wants both the access and the control.

Methods / Procedures

Built in three tiers over seven days, so each tier is a complete project if time runs out. The riskiest unknown — whether a free account can reach a local server at all — was tested on day two, before the document pipeline was started.

Evaluation, three axes. Function: the chain decomposed into seven links, each recorded as pass, fail or untested, and a link counts only when observed running. Safety: adversarial testing, where a case passes only if the attempt is refused and the refusal is logged. Cost: marginal cost to the student, with token efficiency as one sub-metric.

Discussion of Results

The saving is not in the conversion. MarkItDown output is within a few percent of the raw text, and usually slightly larger. What saves is sending two pages instead of six — and that is only possible because the file never leaves the machine. The model is given a path, not a copy, so it asks for the pages it needs.

Two failures were found by reading, not by testing. The empty token, and a search path that returned unfenced text. Both passed a green suite. That is the answer to the secondary question, and it is why the end-to-end run matters more than the tests.

Errors and Limitation Gaps

  • No delivery. Pip prepares the prompt; the paste is manual. The automatic paste depended on the chat vendor's markup and could not be verified without a live account, so it was removed rather than risked.
  • Tier 3 needs the internet. The chat client is cloud-hosted, so the tunnel must be up. No local-only client was built.
  • No user study. The survey instrument exists and was not administered. No claim about usability is made.
  • macOS only. Windows path handling is untested.
  • Open by design. A folder can be swapped between validation and conversion. Closing it needs OS-level isolation, not JavaScript.
  • Not distributable. The app runs from a checkout. Packaging is four phases of work, listed below.

Conclusion

A student on a free tier can have agent-like access to their own files without paying for it — with a boundary they set, can revoke, and can read back afterwards.

The saving comes from reading less, not from converting better. And the boundary is not decoration: it is the thing that makes scoped reading safe enough to allow.

Future Research

  • Package it. Bundle the converter and the tool server, add a first-run panel, sign it.
  • Administer the survey. Ten to twenty students, timed task, before and after.
  • Scanned PDFs. Currently return zero pages; needs OCR.
  • Windows, and a per-tool rate limit.
